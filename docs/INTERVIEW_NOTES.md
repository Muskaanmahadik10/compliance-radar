# Explaining ComplianceRadar in an interview

## 30-second pitch

"ComplianceRadar is a prototype on synthetic company data. You poll regulatory and news feeds, a Redis Streams worker classifies each item with rules, a LoRA-fine-tuned encoder and an LLM, and for an event you pick, a LangGraph pipeline works out which suppliers, parts and products are affected. Those come from SQL, not the model. It drafts an impact brief with citations to the company's own policies and contracts. A deterministic verifier removes ids and citations that aren't in the SQL result or the retrieved evidence, an LLM critic reviews the draft, and a person approves it before tasks are created. An AI assistant built the first version and a second AI audited it. I verified the audit's findings and fixed the ones that changed results, and I can walk you through them."

## The audit story (lead with this when asked "what did *you* do?")

An AI coding assistant built the first version; a second AI (Codex) audited commit `af9dd6b` and reported 47 grouped findings. I checked each against the code before touching anything. The ones I fixed, each now covered by a regression test (`tests/test_audit_fixes.py`):

| Finding | What was wrong | Fix |
|---|---|---|
| LLM classifier tier never ran live | The worker, API and UI called `process_available()` without the LLM callback; only the evaluation script passed it. The 3-tier result was an offline path. | One factory (`classify.llm_callback`) used by all entrypoints and the evaluation; each event stores which tier decided it. |
| Erased documents came back | Erasure never touched `documents.json`, and ingestion re-read it. The UI also rebuilt the corpus when the collection was empty. | Tombstone table written first; every ingest/rebuild skips tombstoned ids; source copies removed; bootstrap never recreates. Test: erase → re-ingest → rebuild → still gone. |
| Retrieved passages skipped masking | Only the question and history were masked. | One redaction function for every provider-bound text, including brief evidence. |
| Dates masked as phone numbers | "2026-11-13" became "[phone]", which also changed the search query. | Dates matched first and kept; phones need ≥ 9 digits. |
| Certificate signed with a public key | Default key was in the repo, so anyone could re-sign an edited certificate. | Certificates carry a key id; a demo-key signature is labelled integrity-only and never counts as authentic. |
| Prompted deadline too long for Postgres | The prompt's own example was 37 characters; the column was `varchar(32)`. Approval would fail in compose mode. | `TEXT` column plus an idempotent migration; test with the 37-character example. |
| Mandatory research queries dropped | Two safety queries were appended and then the list was cut to 5. | Reserve their slots first. |
| Verifier gaps | Invented product ids passed; a policy entry could borrow another policy's citation; "999 suppliers" in the summary passed; a critic approval overrode an uncited action. | Product ids checked, names replaced with the record's, entries bound to their own document, explicit totals checked against SQL; structural failures block automatic approval. |
| Metric names that didn't match | "grounded_first_try" read the *final* findings; impact compared counts, not ids. | Per-attempt records; supplier id sets; old results kept in `artifacts/superseded_af9dd6b/`. |
| Silent mock, unused budget, no `.dockerignore` | A missing key quietly became the mock; `max_cost_per_brief_usd` was never read; `COPY . .` would copy `.env` into an image. | Missing key raises; budget enforced; `.dockerignore`. |

What I deliberately did *not* fix, and say so: authentication, pending-message recovery, a transactional outbox, idempotent task publication, verbatim-quote checking, Langfuse wiring. They are listed in the README's Limitations.

## Design decisions and the questions they answer

| Question you'll get | Answer |
|---|---|
| Why LangGraph and not a simple chain? | The work has a shape: fan out research per sub-question in parallel (`Send`), loop back once if the review fails, then pause for a human (`interrupt`) and resume from a checkpoint (SQLite locally, Postgres in compose). You could build that by hand, but LangGraph provides the state, fan-out and checkpoint/interrupt primitives. |
| How do you stop hallucinated suppliers or numbers? | Exact, named checks, not a universal guarantee. (1) Counts and impact lists come from SQL; the model's schema has no field for them, and the full id lists are stored with the brief. (2) The verifier removes supplier/part/product ids not in the SQL result, replaces names with the record's, removes citations whose section was not retrieved, removes a supplier's citation of another supplier's contract, and flags explicit totals in the summary that differ from SQL. (3) An LLM critic judges whether passages support claims. What it does *not* check: verbatim quotes, obligation direction, deadlines. Those need the critic and the human. |
| Why hybrid search and a reranker? | Measured on a small synthetic set: on paraphrased questions BM25 alone gets 0.40 hit@1, dense 0.64, fusion 0.52 hit@1 but 0.84 hit@5, and the reranker lifts hit@1 to 0.76 at about 25× the latency. On direct questions everything is near 1.0, which is why I built the harder set. |
| Is it real-time? | No, and I don't claim it. Polling is user-triggered (a button or `POST /ingest/poll`), and a person picks the event to brief. The worker is stream-based (consumer group, dedupe), and chat answers stream over SSE. A scheduler and an event-to-brief consumer are the next step. |
| Did fine-tuning help? | Topic accuracy on 52 hand-written English headlines: rules 31, LoRA alone 42, rules → LLM 48 with 24 LLM calls, rules → LoRA → LLM 49 with 5 calls. So the encoder is weaker than the LLM alone, but as a middle tier it removed 79% of LLM calls with comparable accuracy on this set. One headline of difference is not significant. That cascade was measured offline; the live worker only runs it since the audit fix, and I haven't re-measured live. |
| What did the critic actually catch? | In the pre-audit 11-event run it rejected 4: two real errors (a clause cited in the wrong direction; one supplier's contract used for another) and two over-strict calls. I turned the real class into a deterministic rule and fixed the critic's instructions. Those numbers used the old metric definitions, so they're kept as superseded, not as headline results. |
| And after the fixes? | One small real-model check (first 3 replay events): supplier id sets exact 3/3, every action cited 3/3, critic approved 1/3. The two rejections were real: an action claiming a 15-day breach-notice duty that the cited clauses don't contain, and a summary saying 8 tier-1 suppliers where SQL says 11. Both had valid citations, which is exactly why citation checks alone aren't enough. The run also exposed a bug in my new count check: it read "tier‑1" with a non-breaking hyphen as "1 suppliers". I fixed it with a regression test. |
| A bug you found yourself? | After a restart the deduper remembered stored ids but not titles, so a near-duplicate of the same regulation was stored twice. The idempotency test caught it; the fix re-seeds the LSH from the database. |
| A production-style failure you handled? | The free tier's daily token quota ran out mid-evaluation. My first diagnosis (request too large) was wrong; the error said "tokens per day, try again in 28 minutes". Now the retry policy parses that: it waits out per-minute limits, sends daily-quota failures to the smaller model, and records which model wrote the brief. |
| How is cost controlled? | A router sends cheap steps to a small model and drafting/critique to a larger one. A callback estimates cost from reported tokens and a price table (an estimate: unknown models count as $0), and a per-brief budget stops further model calls once spent. |
| What about confidential data? | Embeddings, BM25 and reranking run locally. Only selected passages go to the LLM, with e-mail addresses and phone numbers masked (nothing else is detected). The provider can be a local model via one env var. |
| Prompt injection? | Retrieved text is treated as data: instruction-like passages are redacted, `web_fetch` is allow-listed, and there's no tool to approve a brief. Limits: the redaction is pattern-based, and tool permission labels aren't enforced at dispatch. |
| What does erasure mean here? | Retrieval erasure with recorded checks: tombstone first, vector chunks and local source copies deleted, then checks that probes built from the document's own wording no longer retrieve it and answers don't cite it. It's a record of checks at a point in time, not proof of zero influence. Briefs that quoted it are listed, not redacted. No model here was trained on the documents, so unlearning, my thesis topic, isn't needed for this case. |
| Why synthetic company data? | Real supplier masters are confidential, and evaluation needs ground truth ("this event affects exactly these suppliers"). Feeds are real public sources; a replay fixture makes tests deterministic. |
| How do you test LLM code in CI? | A deterministic mock implements the LangChain interface, including structured output, so 54 tests and the mock evaluation run with no key. A second CI job runs the same tests against real Qdrant, Redis and Postgres containers. The mock critic always approves, so mock results check plumbing, not quality. |

## What I would do next

A scheduled poller plus an event-to-brief consumer with pending-message recovery; verbatim-quote matching against stored source spans; authentication; a full 11-event real-model rerun with the corrected metrics; a Traditional Chinese evaluation set; a fresh classifier test set to validate the 0.8 threshold.
